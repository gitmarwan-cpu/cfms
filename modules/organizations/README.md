# Module: Organizations & Structure

جزء من **Core Platform** — الأساس الذي تُبنى عليه كل وحدة أعمال.

## الكيانات

| الكيان | الغرض |
|---|---|
| `Organization` | المؤسسة (المستأجر/Tenant). تحمل `slug` فريد للبوابة العامة، الهوية البصرية، الإعدادات. |
| `Organization Node` | عقدة تنظيمية (فرع/قسم/قطاع...) ضمن `organizations`، هرمية عبر `parent_id`، بلا حد لعدد المستويات. |
| `Organization Node Type` | نوع العقدة التنظيمية (قابل للتخصيص لكل مؤسسة عبر `org_unit_types.organization_id`)، مع `hierarchy_level` اختياري. |
| `UserOrganization` | عضوية مستخدم في مؤسسة (M:N حقيقي) — مستقل عن الصلاحية (قد ينضم بلا أي دور). |

## الهيكل التنظيمي مرن، وليس ثابتاً

**لا** جداول منفصلة ثابتة لـ "فرع"/"قسم"/"فريق" — نوع العقدة التنظيمية نفسه بيانات
تُدار من لوحة الإدارة لكل مؤسسة، تسمح بأي تسلسل هرمي مخصَّص (مثال: قطاع ←
فرع ← قسم ← فريق، أو أي تركيب آخر تحدده المؤسسة).

## نموذج الهيكل التنظيمي المعتمد (Canonical Organization Hierarchy Model)

### CURRENT ARCHITECTURE — البنية الفيزيائية

جدول `organizations` هو **الجدول الفيزيائي الوحيد** الذي يمثل:

1. المؤسسة/المستأجر (Tenant) نفسها — وهي **العقدة الجذر** للهيكل.
2. كل الوحدات التنظيمية تحتها (فروع/قطاعات/أقسام/فرق...) — كعُقد تنظيمية.

لا يوجد كيان جذر منفصل (RootOrgUnit) ولا عقدة جذر اصطناعية، ولا جدول
`org_units`، ولا جداول فيزيائية حالية منفصلة للفروع/القطاعات/الأقسام/الفرق —
كلها تُمثَّل بعُقد داخل `organizations`.

### ثوابت العقدة الجذر (المؤسسة نفسها)

| الحقل | القيمة |
|---|---|
| `parent_id` | `NULL` |
| `org_unit_type_id` | `NULL` — الجذر ليس وحدة تنظيمية ولا يحمل نوع وحدة |
| `root_organization_id` | `NULL` — الجذر يشير إلى نفسه ضمنياً |

### ثوابت الوحدات التنظيمية تحت الجذر

| الحقل | المعنى |
|---|---|
| `parent_id` | الأصل المباشر — **الحقل المعتمد (canonical) لتعريف التسلسل الهرمي** |
| `org_unit_type_id` | مُميِّز نوع الوحدة التنظيمية؛ لا يُعرِّف التسلسل الهرمي بنفسه |
| `root_organization_id` | معرّف المؤسسة الجذر/المستأجر — **مرجع دائم لحدود المستأجر (tenant boundary)**: لا يُزال ولا يُعاد تسميته ولا يُوصف بأنه مؤقت/انتقالي |

### قواعد الوضع في الهيكل

- تُسمح **عدة وحدات عليا** تحت العقدة الجذر مباشرة.
- وحدة تُنشأ بلا `parent_id` صريح تُلحق مباشرة تحت العقدة الجذر للمؤسسة،
  ولا يُنشئ ذلك جذراً ثانياً إطلاقاً.
- `parent_id` هو علاقة الهيكل الفعلية؛ `org_unit_type_id` تصنيف/تمييز فقط.

### تمييز مهم: حقلان متشابهان بالاسم

- `organizations.root_organization_id` — جزء من البنية المعتمدة (حدود
  المستأجر)، كما في الجدولين أعلاه.
- `org_unit_types.root_organization_id` — حقل **قديم (LEGACY)** في جدول أنواع
  الوحدات، **ليس** جزءاً من البنية المعتمدة: لا تُكتب قيمته من الكود الحالي،
  ولا يُبنى أي منطق جديد عليه، ولا يُخلط بينه وبين حقل `organizations`.

### CURRENT IMPLEMENTATION CONSTRAINT — قيد تنفيذي حالي: `allowed_parent_type_id`

- `parent_id` يبقى علاقة الهيكل الفعلية، و`org_unit_type_id` يبقى مُميِّز النوع.
- `allowed_parent_type_id` (عمود في `org_unit_types`) هو **قاعدة تحقق تنفيذية**
  في طبقة الخدمة: لبعض أنواع الوحدات تقيّد نوع الأصل المسموح به عند
  الإنشاء/التحديث. الأنواع التي لا تعلن عن قيد تبقى مرنة الوضع داخل المؤسسة.
- هو **ليس** بنية هرمية منفصلة ولا بديلاً عن `parent_id`، ولا يُوصف بأنه
  يعرّف الهيكل.
- حالته طويلة الأمد (إبقاء/تبسيط/إزالة) **FUTURE/DEFERRED** — قابلة للمراجعة
  المنفصلة، ولا يُعتبر عقداً معمارياً نهائياً.

## تعدد الانتماء (Multi-Organization Membership)

مستخدم واحد قد ينتمي لعدة مؤسسات (`UserOrganization`)، بدور مختلف في كل منها
(`UserRole` يحمل `organization_id` منفصلاً لكل تعيين). نظام Groups أُزيل نهائياً؛
لم تعد جداول/عضويات Group موجودة في قاعدة البيانات.
`users.default_organization_id` مجرد إشارة سريعة (denormalized) للمؤسسة
الافتراضية عند الدخول — **ليست** مصدر الحقيقة (المصدر الحقيقي `UserOrganization`).

## البوابة العامة لكل مؤسسة

`organizations.slug` هو المعرِّف العلني المستخدم في رابط البوابة العامة
(`/api/public/:orgSlug/...`) لتحديد المؤسسة لمستفيد غير مسجَّل دخوله إطلاقاً.

## Bootstrap (التنصيب الأول)

مؤسسة افتراضية + أول Super Admin تُنشآن **مرة واحدة فقط** عند أول تشغيل
(`seed-bootstrap-default-organization`، حارس صريح يتحقق أولاً أن لا مؤسسة
موجودة إطلاقاً). **لا** يُنشأ مؤسسة جديدة تلقائياً لكل مستخدم جديد — إنشاء
مؤسسات إضافية يتم يدوياً عبر Super Admin حالياً (SaaS Onboarding التلقائي
مؤجَّل، البنية جاهزة له لاحقاً دون تعديل النموذج الأساسي).
